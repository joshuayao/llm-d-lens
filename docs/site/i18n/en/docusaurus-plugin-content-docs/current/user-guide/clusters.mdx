Add a cluster before creating storage or deploying a model.
Use its kubeconfig to connect an existing cluster, or use Kubespray to create one on your machines.

On wide screens, a left column contains **Target cluster** and its deployment
shortcuts above the searchable **Clusters** list. The selected cluster's health
and edit action stay with the selector; its overview appears on the right.
On narrow screens, these panels stack above the overview. Cluster cards retain
their per-cluster action menus.

## Before you begin: proxy exclusions

If Kubernetes components use an HTTP(S) proxy, keep cluster-internal traffic off it.
Set `NO_PROXY` and `no_proxy` to the same value, preserving existing exclusions and
including localhost, node hostnames/IPs, the API server address, Service/Pod CIDRs,
and cluster DNS suffixes. Example (replace the placeholders and adapt `cluster.local`
if your cluster uses a different DNS domain):

```text
localhost,127.0.0.1,::1,<node-hostnames-and-IPs>,<api-server-host>,<service-CIDR>,<pod-CIDR>,.svc,.svc.cluster.local,cluster.local
```

**Verify these settings on the running `kube-apiserver` process**, not just in a shell
or Lens. For kubeadm, configure its environment in
`/etc/kubernetes/manifests/kube-apiserver.yaml`; kubelet recreates the static Pod,
briefly interrupting API access. Keep manifest backups outside that directory.
CIDR exclusions alone do not cover Service DNS names: missing DNS exclusions can
route webhook calls through the proxy and cause TLS errors or timeouts.

## Register a cluster from a kubeconfig

### Kubeconfig permissions

Lens keeps the kubeconfig you register. It does not create a ServiceAccount,
ClusterRole, ClusterRoleBinding, replacement kubeconfig, or a dedicated Lens
identity for the cluster handoff. Orchestration administrator work is a temporary operation
script, not a credential you install in Lens.

The clearest setup uses an edit kubeconfig that can run normal namespaced
operations. Some cluster-scoped operations may need an orchestration administrator. Lens shows
those as a separate handoff instead of asking for broader credentials. When using a namespace-scoped `edit` ServiceAccount kubeconfig, Lens automatically
aligns default `create-secret` HF token and handoff namespaces onto the edit
kubeconfig's writable namespace (never overwriting explicit custom namespaces or
existing secrets), so you do not have to change namespaces manually. For cluster-scoped
or cross-namespace storage volumes, Lens defaults new PVCs to a dedicated
`lens-storage-<cluster-id>` namespace (in `create` mode, e.g. `lens-storage-283db094`);
for Non-Admin users, the Orchestration administrator bootstrap script automatically
creates a per-namespace `Role` and `RoleBinding` (`lens-storage-operator`) so the
kubeconfig can manage PVCs and model-cache Jobs in that namespace without manual
RBAC setup.

### Configure the plan

The 9-step Create Cluster wizard saves a provisioning plan without installing
anything on the target cluster. **Review** shows the saved plan preview
(including the Monitoring summary) and does not run a permission check.

Inside the **llm-d stack** step, you can optionally override the **vLLM image** (`vllmImage`) with a custom OCI container image reference (requiring a `:tag` or `@sha256:` digest). When left empty, the default comes from the selected hardware profile (`runtime_image`). Image pre-pull (both direct admin execution and Orchestration administrator scripts) and model deployments use this cluster image, with per-deployment explicit overrides taking highest precedence, followed by the cluster `vllmImage`, and then the hardware profile default.

Also inside the **llm-d stack** step, **Monitoring** is mandatory and supports two modes:

- **`managed` (default)**: Installs `kube-prometheus-stack` (Prometheus, Grafana,
  `kube-state-metrics`, `node-exporter`, Alertmanager, and Monitoring CRDs),
  `llm-d` Grafana dashboards, cluster-wide `llm-d-prism-metrics-reader` RBAC,
  and co-installs the selected accelerator exporters (profile-driven, such as
  NVIDIA DCGM Exporter or Intel XPU Manager). You can configure the Monitoring
  namespace (default `lens-monitoring-<cluster-id>`, e.g. `lens-monitoring-283db094`), optional Prometheus and Grafana
  NodePorts (`30000`–`32767`), and an optional Monitoring host/IP.
- **`existing`**: Connects to an existing Prometheus instance (`prometheusUrl`
  required, `grafanaUrl` optional, Monitoring namespace, and a toggle to install
  missing accelerator exporters and `llm-d-prism-metrics-reader` RBAC).

Choose **Preflight** to open the **Execute** step
and evaluate the plan against the edit kubeconfig, splitting it into:

- **User operations**: Lens runs these with your kubeconfig.
- **Orchestration administrator operations**: Lens does not run these; you send the generated
  script to an orchestration administrator.
- **Lens operations**: local follow-up work such as gateway exposure or model
  cache job fan-out. Lens runs these during **Complete**.
- **Blocked operations**: user-owned secret work or Lens operations whose
  required kubeconfig access is missing. Grant the required access or adjust
  the plan, then re-check; these never go to an orchestration administrator.

When you save the **Model Cache** step with a new Hugging Face token, Lens
encrypts and stores the token temporarily for the draft. It is never placed in
the provisioning plan or orchestration administrator handoff script, and is never displayed
back in plaintext. When you resume a draft later (even after closing the browser
or switching tabs), the wizard preserves the saved state (`Saved for this
draft`), lets you continue **Preflight** and **Execute** without re-entering the
token, allows replacing it if needed, and automatically deletes the temporary
draft copy once the cluster is finalized or discarded.

### Run Preflight

**Review** is a clean plan preview without permission checks. Preflight
needs the saved plan and the Hugging Face token; clicking **Preflight**
immediately opens the **Execute** step and runs the permission check there first,
loading or generating the orchestration administrator script when needed. It does not auto-start
any user operation. Resuming a draft to Review also waits for this explicit action.

- **Ready**: Once the permission check passes, click **Execute** to start running
  user operations. A kubeconfig with full cluster permissions (equivalent to
  `cluster-admin`) passes preflight directly as **Ready** with zero
  Orchestration administrator handoff script and no **Waiting for marker** step —
  Lens executes all setup operations automatically on **Execute** (including
  namespace creation, chart-sourced CRDs such as `lws.crds`, and profile-driven
  remote Kustomize overlays such as NFD or non-DRA device plugins once the
  cluster-wide wildcard SSAR check succeeds).
- **Orchestration administrator operations**: Execute shows the script and
  **Re-check**. User operations stay disabled until re-checking verifies the
  marker, supplies a token, and leaves no admin operations remaining, after
  which you click **Execute**.
- **Blocked**: Execute shows the user-owned access to fix and keeps user
  execution disabled.

### Orchestration administrator handoff

When the split contains orchestration administrator operations, Lens shows:

1. The orchestration administrator operation list and readiness checks (under **View operation details**).
2. A downloadable, idempotent orchestration administrator script.
3. A **Re-check** action that re-checks permissions and verifies orchestration administrator completion.

Send the script to an orchestration administrator. They run it once with their own
orchestration administrator credentials. The script contains only the plan's orchestration administrator
operations; it does not contain your kubeconfig, a Lens identity, or a secret
value. It writes a completion marker when every orchestration administrator operation and its
readiness check passes, including any assigned `prometheusNodePort`,
`grafanaNodePort`, and `monitoringHost` discovered for `managed` monitoring.

After the orchestration administrator finishes, choose **Re-check** in Lens. Lens re-checks
permissions, reads the marker, records the orchestration administrator operations as done,
auto-discovers and persists the Monitoring endpoints and probes Prometheus
health without manual port entry, and acquires the execution token once
complete. The user operations stay disabled until that verification succeeds.
If the marker is missing, partial, stale, or unreadable, Lens explains which
orchestration administrator operations remain and does not start the user run.

For partial-privilege kubeconfigs, when any operation lacks permissions (or
requires the cluster-wide wildcard check), Lens automatically promotes its
unfinished upstream dependencies (excluding user-owned secrets and Lens-side
verification steps) into the Orchestration administrator script so prerequisites
stay ordered cleanly.

With a **kubeconfig with full cluster permissions**, Lens executes monitoring and accelerator exporter
installation directly, discovers NodePort endpoints, persists derived URLs, and
verifies Prometheus readiness during **Complete**. With a **partial-privilege (`edit`)
kubeconfig**, self-contained monitoring and exporter installation is included in
the single downloaded Orchestration administrator script.

### Execute user operations

After Preflight opens **Execute** and the permission check passes (or orchestration administrator
handoff is verified), clicking **Execute** runs the user operations in dependency
order, and **Setup progress** appears once execution starts. Each operation may ask for a
readiness wait; a failed wait stops the run without marking the operation done.
Operations already recorded as done are skipped when you resume.

The execution token is created by handoff verification or by the first user
operation. Later operations reuse that token. If the plan changes, Lens marks the
old run stale and asks you to review the new split.

A **403** means Kubernetes rejected the operation despite the preflight. Lens
refreshes the split and moves that operation into the orchestration administrator handoff while
keeping completed user operations. A **401** means the kubeconfig is invalid or
expired. A **504** means the operation applied but did not become ready; retry
after the cluster resources settle. Other errors identify the operation that
failed and keep completed work.

### Complete

**Complete** runs the remaining Lens-local operations, verifies that every
operation is user-done, administrator-done, or Lens-done, and finalizes the
cluster in one step. The cluster then leaves draft state. If a Lens operation
fails—including a **403** permission denial, which also refreshes the
permission check—the execution token is kept so you can fix access and retry
Complete.

### Upgrade from the pre-M5 step flow

Drafts created before M5 used a separate step ledger. That ledger is not
migrated. Re-open the draft, run **Preflight**, and execute the operation list
again. A completion timestamp alone is not sufficient: only a
completion whose plan hash matches the current plan is treated as complete.

### Credential rotation is separate

Do not upload a replacement kubeconfig in the permission handoff. Kubeconfig
replacement is a separate cluster-settings action for credential rotation. It
does not rerun the permission check or change the provisioning plan.

## Bootstrap a new cluster via Kubespray

1. Open **Clusters → Add** and enter the cluster name.
2. Choose **Bootstrap a new cluster via Kubespray**.
3. For each machine, enter **Host(s)**, **Port**, **Role(s)**, **Username**, and an **SSH private key** or **SSH password**. Use **Add node** for more machines.
4. Under **Network proxy for target nodes**, keep **Auto** to reuse each machine's settings, or choose **Custom for these nodes** and enter the proxy.
5. Click **Run preflight**. Fix failed checks and run preflight again until every host passes.
6. Click **Start bootstrap** and follow its progress.
7. When the generated kubeconfig appears, continue through the registration steps above to **Complete** and **Done**.

Bootstrap changes the target machines. Check their addresses and roles before starting.

## Edit a cluster

1. Select the cluster, then click **Edit cluster**.
2. Change its name, description, proxy, **HF_TOKEN secret**, **vLLM image** (`vllmImage`, or reset it to empty to use the selected hardware profile's `runtime_image` default), model-gateway settings, or monitoring settings (**Monitoring mode**: `Managed` vs `Existing`, and in `Existing` mode, external **Prometheus URL** and optional **Grafana URL**; in `Managed` mode, endpoints and NodePorts are discovered automatically and displayed read-only).
3. Click **Save changes** and check that the updated values appear.

Component versions are supplied by the Lens release and are not editable here.

### Rotate the HF_TOKEN secret

**HF_TOKEN secret** holds the Hugging Face token this cluster uses to pull gated
models. Lens stores only the Secret's namespace and name; the token value lives
on the cluster and is never shown again.

1. Leave **New token** empty to keep the current token. Type a token only when
   you want to replace it.
2. Change **Namespace** or **Secret name** only to point the cluster at a
   different Secret; Lens creates that Secret when it does not exist yet.
3. Click **Save changes**. The confirmation names the Secret that was written.

Deployments and Model Cache downloads copy the token into their own namespace
when they run, so workloads that are already running keep the previous token
until you recreate them.

## Check model gateway access

1. In **Clusters → Edit cluster**, check **Gateway host/IP** and **Gateway exposed port** against the address clients can reach.
2. Open **Model services** and locate this cluster's **Gateway** node.
3. Open the node menu and choose **Install** if the gateway is absent, or **Reconcile** to apply its saved settings.
4. Follow the operation logs, then [publish a model service and send a request](/tutorials/publish-a-model-service).

If installation or requests fail, use [Troubleshooting](/troubleshooting).
The create/edit wizard currently offers **Istio**; instructions for manually
repairing other providers belong to troubleshooting, not the normal registration flow.

## Review cluster health

The cluster list refreshes quietly every five seconds while the page is visible.
The selected cluster's health refreshes every five seconds; other clusters' health
refreshes every ten seconds. No manual refresh is needed. List refreshes preserve
the current selection and search, and retain existing entries with an error message
if an update fails.

1. Select a cluster in **Clusters**.
2. Check **Workers**, **CPU**, **Memory**, **Deployable GPU**, **VRAM**, **Disk**, and **Monitoring**.
   **Memory** and **Disk** lead with the capacity still free out of the cluster
   total, and show the percentage already in use on the **Usage** line below.
   A dash means the cluster cannot report that reading right now, not that
   nothing is free.

Clusters shows infrastructure health and worker nodes, not deployment lists or
individual deployment failures. Click **Deployments** below **Deploy a model** in the
**Target cluster** panel to open the
[Deployments page](/user-guide/deployments) with the selected cluster already set
in its filter. You can change or clear that filter; the entry URL preserves it on reload.
Use that page to manage deployments, endpoints and logs. Deployment monitoring and profiling
remain available through [Observability](/user-guide/observability).

Click **Model services** below **Deployments** to open
[Model services](/user-guide/model-services) with the same cluster preselected in
the service-flow filter. This filter can also be changed or cleared, and its entry
URL restores the cluster on reload or browser history navigation.

When accelerators use DRA, Lens reads their model from ResourceSlice device attributes
even if nodes do not have GPU product labels. The reported model is used to select
the matching AISimulate system for hardware-aware recommendations.

When Monitoring is configured, Lens fetches live node, CPU, memory, disk, and
accelerator telemetry directly from Prometheus over HTTP, supporting restricted
namespace-scoped kubeconfigs without cluster-wide `nodes` RBAC.

The **Monitoring** health card aligns with [Observability](/user-guide/observability)
across both orchestration administrator and non-admin kubeconfigs and both `managed` and `existing`
monitoring modes:

- **Orchestration administrator + `managed` mode**: verifies the Kubernetes monitoring stack directly.
- **Non-admin kubeconfigs and `existing` mode**: probes the configured Prometheus and
  Grafana HTTP endpoints, counting only applicable components (optional Grafana in
  `existing` mode and accelerator exporters on CPU-only clusters are excluded from the
  required count).

Clicking the **Monitoring** card navigates directly to
[Observability](/user-guide/observability). When monitoring is degraded, unreachable,
or not configured, the overview banner provides role- and mode-appropriate guidance:

- **Orchestration administrator (`managed`)**: install or reinstall the monitoring stack in
  **Observability**.
- **Orchestration administrator (`existing`)**: configure external Prometheus and optional Grafana URLs via
  **Edit cluster** on the **Clusters** page, then click **Re-check** in **Observability**.
- **Non-admin**: configure external Prometheus and Grafana URLs via **Edit cluster** on the **Clusters** page,
  or click **Install** / **Reinstall** in **Observability** to run the **Orchestration administrator** setup or
  repair script, then click **Re-check**.

## Put worker nodes into maintenance mode

1. In the cluster's **Workers** list, select the nodes.
2. Click **Enter maintenance mode**, review the names, then click **Cordon nodes**.
3. After maintenance, select the nodes, click **Exit maintenance mode**, and confirm **Uncordon nodes**.

**Cordon stops new pods from being scheduled; it does not stop or move existing pods.**
Plan any required workload shutdown or migration separately.

## Delete a cluster registration

1. Open the cluster's **Actions → Delete cluster**.
2. Check the cluster name and the deletion warning.
3. Click **Delete**.
   - If your kubeconfig has permission to delete all Lens-owned resources, Lens removes them and deletes the registration immediately.
   - If your namespace-scoped `edit` kubeconfig cannot delete cluster-scoped or cross-namespace resources (or the cluster is unreachable), the modal switches to **Orchestration administrator cleanup required** (or **Cluster unreachable** when offline).
4. When **Orchestration administrator cleanup required** or **Cluster unreachable** appears:
   - Copy or download the idempotent cleanup script and send it to an orchestration administrator to run.
   - Once the orchestration administrator runs the script, click **Re-check & Delete** (or **Retry & Delete** when unreachable) to verify the completion marker and remove the registration.
   - If the completion marker cannot be verified automatically (`unconfirmed`) or the cluster is unreachable, check the explicit confirmation box and click **Confirm & Delete Record** to remove the registration from Lens.

Lens never deletes `existing-secret:*` secrets, existing or shared namespaces (including `existing`-mode Gateway or secret namespaces), bare `lens-storage`, bare `lens-monitoring`, or legacy `llm-d-bench-storage` namespaces, or protected system namespaces (`default`, `kube-system`, `kube-public`, `kube-node-lease`, `istio-system`, `envoy-gateway-system`, `envoy-ai-gateway-system`, `agentgateway-system`). Cluster-owned `lens-storage-<cluster-id>` and `lens-monitoring-<cluster-id>` namespaces created by Lens (when not shared with another cluster) are deletable during cleanup. When deleting a cluster with `managed` monitoring, Lens cleans up managed monitoring and accelerator exporter resources (using the two-phase orchestration administrator cleanup flow if needed, while preserving resources shared with another cluster on the same Kubernetes API server). In `existing` monitoring mode, Lens never deletes monitoring resources. For a cluster you are still registering, any storage volume created during the wizard is removed together with its PVC and PV, while model files on NFS or hostPath are kept. A fully registered cluster that still has deployments or storage volumes cannot be deleted until you delete those resources first.

## Cannot see a cluster?

Ask an administrator to check your cluster assignment. Maintainers manage assigned
clusters; administrators can manage all clusters.
